# Security

## Exposed surface

The API binds to loopback. Remote access is intended through Tailscale Serve HTTPS, with a separate Workspace token even inside the tailnet. The browser uses an HttpOnly, SameSite=Strict cookie (Secure on HTTPS). The server checks Host and Origin, limits login attempts and request size, applies CSP, and authenticates screenshot access. State-changing browser requests require an exact allowed Origin; GET routes do not change state. A worker has its own token and must present the current project-qualified lease nonce. This is a single-owner local model: the owner token intentionally reaches every configured project. Project-specific human roles are outside the v1.0 operating model. Do not share the owner or worker token.

Encrypted backups contain the SQLite queue, decisions, history, project configuration, local environment and design screenshots. `WORKSPACE_BACKUP_KEY` is stored in the ignored `.env` and must also be kept in an offline location for recovery. Backup files use authenticated AES-256-GCM encryption and are verified before retention pruning or restore. SQLite snapshot and verification briefly stage plaintext under the current user's OS temporary directory and remove it after normal completion; an abnormal process termination can leave a `workspace-snapshot-*` or `workspace-verify-*` directory there for local cleanup. Backups do not include Git repositories, task worktrees, or provider login directories. An attacker with access to both a backup and the key can read the contents. Backup failure stops the local launcher; restore requires the server to be stopped and referenced worktrees to exist. Restore preserves current credentials by default; `--restore-credentials` explicitly reinstates archived tokens.

The browser cannot register repositories or arbitrary test commands. Repositories and checks come from local `projects.json`. Tasks run in separate Git worktrees and never merge, push or deploy automatically. Worktrees share Git object metadata with their source repository; they are not an OS sandbox. Protected-path changes produce `UNVERIFIED` instead of approval.

## Process boundaries and tested results

Claude Code runs with the official `--restricted` and `--strict-mcp-config` modes, without Bash, PowerShell, code execution or WebFetch tools. A real Claude CLI probe denied both a Read and an Edit of a controlled file outside its worktree (`npm run test:provider-boundary`). This confines its built-in file tools; the Claude process still holds its subscription authentication and other resources available to its OS account.

Windows Codex CLI 0.164.0 still fails before loading AGENTS.md when an actual `codex exec` uses the custom MXC profile: the child environment lacks `SYSTEMROOT`. The Windows provider now requires WSL2 Ubuntu and the audited Linux Codex 0.164.0 profile with root deny, a scoped Worktree mount, explicit secret-file denies, and no network. It does not fall back to broad-read `workspace-write`. `npm run test:codex-boundary` observed six operations in a real Codex AI session: allowed Worktree read/write succeeded; outside Workspace data read/write and installed-dependency/cache writes failed. The outside canary did not appear in output. Each run performs deny probes before execution. The Workspace creates empty mount target directories before launching Codex so synthetic sandbox placeholders cannot appear in the reviewable diff; a conflicting file or symlink blocks execution. WSL is part of the trusted host; this confines the Linux subprocess but is not a separate VM security boundary against an administrator or kernel attack.

Windows Node and Expo verification commands run in WSL through root-deny profiles under bounded systemd scopes. `npm run test:sandbox-check` passed sample syntax and test commands; `npm run test:wsl-check-boundary` read an allowed file and denied a Workspace data canary. Linux dependencies are installed with configured `npm ci --ignore-scripts` before checks, without package lifecycle scripts. Remote lockfile entries require approved registry URLs and integrity hashes; npm config uses `/dev/null` and a unique per-run cache. The dependency setup profile has network access only while fetching reviewed packages; its filesystem boundary probe denied an outside read and a persistent host write. A shadowed denied write can report success inside MXC while leaving the host canary unchanged.

Spring checks route to WSL instead of the broader-read Windows MXC check profile. The trusted, committed Gradle build first resolves dependencies in a root-deny setup scope. Subsequent Gradle tests use `--offline` inside a nested user/network namespace with loopback enabled and external egress absent; `test:wsl-loopback` observed a successful local connection and denied external connection. Cached dependency artifacts, including the Byte Buddy agent loaded at JVM startup, are read-only to the check process; `test:be-cache-boundary` verified write denial. OpenJDK 21 and Gradle run under memory, CPU, wall-time and 384-task limits. `test:be-isolation` passed the full configured Momentory BE suite with `BUILD SUCCESSFUL`; Docker-dependent cases may be skipped when Docker is unavailable. The extracted Gradle wrapper distribution is also read-only to checks; the offline Gradle executable is invoked directly from the reviewed cache. `test:be-cache-boundary` denied a wrapper-distribution write.

Provider and check subprocesses do not inherit Workspace tokens or environment variables whose names indicate keys, secrets, passwords, credentials or authentication. Log redaction covers common token forms and exact secret environment values, but is not a complete data loss prevention control. Windows WSL Codex and Node/Expo checks run under systemd memory, swap, task-count and CPU quotas plus CPU and wall-time limits. The resource test observed a 256 MiB memory cgroup and two-second CPU limit killing controlled fixtures; a real Codex session was cancelled and another hit its wall timeout. Worker restart reaped a dead-owner WSL scope. Scope metadata now uses an atomic rename, and WSL user systemd calls set `XDG_RUNTIME_DIR` explicitly after distro restarts. A zero-filled legacy marker is quarantined only after inactive-scope checks across installed WSL distributions; malformed nonzero markers fail closed. A partial Worktree diff remained `STALE`, required its reviewed hash before resume, and resumed without a duplicate claim. Actual Mac npm/sample sandbox, provider cancellation and timeout evidence is recorded in T7_MAC_REPORT.md. Mac cleanup tracks descendant identities at cancellation, including separate process groups; the tracking map is not persistent across a Worker SIGKILL.

## Release limitation

The same dependency marker is required on macOS. The trusted npm path now issued and validated it on a real Mac with a fixed registry-locked fixture. Unmarked mounts, lock/index mismatch, escaping links and changed executable pins fail closed. The setup uses distinct private npm user configuration and /dev/null global/OpenSSL configuration without disabling TLS verification. The Mac POSIX AI profile keeps Gradle/build/output caches read-only. Full FE/Design Lab installation, actual mount replacement and persistent orphan cleanup after a Mac Worker SIGKILL remain unverified; macOS Gradle preparation remains NOT_IMPLEMENTED. See [T7_MAC_REPORT.md](T7_MAC_REPORT.md) for scoped evidence.


The previous sandbox secret-file glob stopped scanning after eight directory levels; an actual depth-10 `.env.local` read was possible. The installed audited profiles now scan to depth 32, and Windows WSL launches reject trees beyond the tested bound before provider or check execution. Real sandbox probes denied depth-10 and depth-23 reads, and a depth-40 fixture blocked execution. WSL interop probes denied direct `cmd.exe` and `/init` execution. Nested Design Lab dependency mounts are created and read-only even before packages are installed. Provider launch accepts only the reviewed `exec --json` argument forms. Approval and dependent-task inheritance compare a persisted fingerprint of the verified Worktree; changing reviewed bytes returns HTTP 409 or blocks inheritance. These controls do not make the host or Windows account untrusted.

Independent review then found four concrete gaps in that commit. The Windows Claude launcher now resolves an absolute `claude.exe` outside the Workspace and task Worktree and launches it without a shell; a local fake executable was ignored and a real Claude Read/Edit boundary session still passed. WSL Codex no longer accepts an executable override and checks the trusted npm package's resolved CLI path before execution. Approved-file inheritance rejects a linked destination ancestor; a junction fixture could not write its payload outside the child Worktree. The Worker claim API requires an explicit `claude` or `codex` provider, and HTTP tests reject omitted and misspelled values. These fixes do not constitute a comprehensive penetration test.

The subsequent path check resolves the Workspace and task roots themselves before comparing a Claude executable, including when the task root is reached through a junction. WSL launches the exact real npm package path it checked. Empty dependency mounts are permitted before setup. Populated root and Design Lab dependencies require a validated locked-installation marker on every platform; unprepared populated and linked fixtures were denied. The selected design apply passed full FE checks after reviewed recovery and remained at an approval gate.


The MXC failure is bypassed only through the verified WSL backend; a missing or changed WSL boundary blocks Windows Codex jobs. Project-specific human roles are not implemented. Physical Tailscale phone access, locked-screen operation, full Mac project acceptance, and native app screens remain unverified. Do not use this build with unknown users or highly sensitive repositories. Tailscale Serve and a phone on another network have not been tested because Tailscale is not installed on the available laptop. No local development port is intentionally exposed to the public internet.
