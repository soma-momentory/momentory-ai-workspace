# Security

## Exposed surface

The API binds to loopback. Remote access is intended through Tailscale Serve HTTPS, with a separate Workspace token even inside the tailnet. The browser uses an HttpOnly, SameSite=Strict cookie (Secure on HTTPS). The server checks Host and Origin, limits login attempts and request size, applies CSP, and authenticates screenshot access. A worker has its own token and must present the current project-qualified lease nonce. A single owner token currently reaches every configured project; project-specific human roles are not implemented.

The browser cannot register repositories or arbitrary test commands. Repositories and checks come from local `projects.json`. Tasks run in separate Git worktrees and never merge, push or deploy automatically. Worktrees share Git object metadata with their source repository; they are not an OS sandbox. Protected-path changes produce `UNVERIFIED` instead of approval.

## Process boundaries and tested results

Claude Code runs with the official `--restricted` and `--strict-mcp-config` modes, without Bash, PowerShell, code execution or WebFetch tools. A real Claude CLI probe denied both a Read and an Edit of a controlled file outside its worktree (`npm run test:provider-boundary`). This confines its built-in file tools; the Claude process still holds its subscription authentication and other resources available to its OS account.

Codex development sessions currently use its `workspace-write` CLI sandbox. Its separate Windows MXC permission profiles under `profiles/` denied a controlled outside file read/write and a `.env` read in direct `codex sandbox` probes. **The profile cannot yet be used for the actual Codex AI session on this installed CLI**: `codex exec` fails before loading AGENTS.md because the MXC launcher receives an environment missing `SYSTEMROOT`. The issue reproduces on Codex CLI 0.163.0, while standalone MXC commands work; see the [related Codex issue](https://github.com/openai/codex/issues/56264). The provider retains the working `workspace-write` mode. Do not equate the standalone sandbox probe with isolation of a Codex AI task.

Configured verification commands run through a separate Codex MXC `workspace-check` profile. The sample `node --check` and `node --test` commands pass inside this profile (`npm run test:sandbox-check`). Momentory FE typecheck, lint and all 126 Jest suites also passed inside MXC. Jest initially failed because MXC's default Windows temporary path fell under the denied home directory; `scripts/sandbox-temp.cjs` now redirects Node temporary files into the task worktree and rejects a symlink escaping it. Direct probes denied reads of the Codex profile, a controlled home-directory canary, and the Workspace SQLite directory. Node needs drive-root metadata traversal, so the check profile allows broad read access outside explicit denied paths. AI-generated project code run by checks may therefore still read unrelated locations. The profile prevents writes outside the task worktree and disables network for sandboxed commands. Project dependency setup uses locally configured commands and currently runs outside this profile before the AI edits code; current Momentory setup uses `npm ci --ignore-scripts`.

Provider and check subprocesses do not inherit Workspace tokens or environment variables whose names indicate keys, secrets, passwords, credentials or authentication. Log redaction covers common token forms and exact secret environment values, but is not a complete data loss prevention control. OS-level memory and CPU quotas are not implemented; executions have wall-clock timeouts and process-tree cancellation. An orphaned child after an abrupt worker death and a partially edited worktree still require stronger recovery evidence. macOS sandbox behavior has not been tested on a Mac.

## Release limitation

The known Codex AI-session MXC failure, broad read access of verification commands, lack of per-project human roles, unverified orphan cleanup, and missing physical network and macOS security tests remain release blockers. Do not use this build with unknown users or highly sensitive repositories. Tailscale Serve and a phone on another network have not been tested because Tailscale is not installed on the available laptop. No local development port is intentionally exposed to the public internet.
